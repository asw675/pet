# 002B 应用用例与原子旅行结算

日期：2026-11-25

## 实现范围

`AppService` 是独立于 Electron 的业务协调层，仅依赖公共契约、领域内核和 `AppRepository`；接收闭合版本化 IPC 请求，使用可信注入时钟、ID 和随机种子，客户端提供的 issuedAt 不控制旅行进度。

- 新档创建两个独立示例角色；实现 7 个公共命令（主宠、互动、显示状态、旅行、召回、报告已读、免打扰/暂停），读取快照不开放数据库接口。
- 全局 revision、逐宠 revision、逻辑时间水位、稳定命令回执；相同 commandId 与相同规范化 payload 精确返回历史结果，冲突拒绝，过期 revision 明确反馈。
- 每宠独立冻结路线及战力，扣除 15 点精力。时间推进按到期节点、petId、tripId 稳定排序；空时间推进不产生虚假业务 revision。
- 对活跃旅行从 seed、冻结快照和已记录召回重放事实与 checkpoint；还原奖励草稿，再将结果写入唯一结算、奖励账本、金币、物品、XP、CG、状态与 outbox 的同一事务，不信任客户端或模型给出的数值。
- 唤醒和重启首先审计已结算历史及活跃状态，然后恢复离线进度，验证快照；损坏记录拒绝启动或操作，不自动覆盖原档。返回摘要保留实际归家时间，原冻结行程和原始 ETA 不改变。
- 数据库永久故障映射为 `SERVICE_UNAVAILABLE`、不可直接重试；业务拒绝及内部异常均返回稳定脱敏错误。

## 验证

Node 26.12.1 / SQLite 3.54.0：服务单元测试 13/13，真实 SQLite 集成测试 7/7 通过，覆盖：

- 重复命令、payload 冲突、旧 revision、两宠独立、回拨/跨日、召回和战败。
- 关闭后离线 72 小时、同一存档重新打开 20 次，事实、XP、金币、材料与 CG 未重复发放。
- 故意在 `TripSettled` outbox 写入前注入失败（已尝试入账其他奖励），确认事实、账本、库存、XP、CG、金币、状态及 outbox 一起回滚，移除故障后成功恢复。
- 合法结构但与回放不一致的奖励草稿被拒绝；已结算账本受控损坏后重启拒绝，不产生新奖励。不完整历史不能误判为新档。
- 仓库故障需重启，返回结果不泄露底层异常。
